微信 Windows 客户端逆向分析报告

WeChat (Weixin) 4.1.15.55 — 基于 Ghidra 12.1 与 PE 静态解析的二进制证据链分析
分析日期：2026-10-17 分析工具：Ghidra 12.1.4 / 自研 PE 解析脚本 / PowerShell 字符串提取 目标路径：C:\Program Files\Tencent\Weixin

一、结论摘要

本次分析针对微信 Windows 客户端 4.1.15.55 版（新架构）。该版本已从旧版 WeChat.exe 单体架构演进为 「启动器 + 巨型核心 DLL」 架构：

  • Weixin.exe（3.0 MB）——轻量启动器，仅静态导入 KERNEL32，通过 11 个延迟加载 DLL 按需载入组件，Ghidra 识别出 7,080 个函数，入口为标准 CRT startup。
  • Weixin.dll（194.8 MB）——承载全部业务逻辑的核心库，含 12 个节区（.text 达 119 MB，估算约 51 万个函数），117 个导出函数，内嵌 Qt 框架元数据节区。
  • 网络栈为 Chromium Cronet（导出命名空间 mmcronet，支持 HTTP/2、QUIC、Brotli），业务协议基于腾讯 Mars 框架与 Protobuf。
  • 所有 .bin 组件（RadiumWMPF 412 MB、XPlayer、WeChatOcr、XEditor 等）实为 ZIP 容器（PK 魔数）。
  • 两个主文件均携带有效的腾讯数字签名（CN=Tencent Technology (Shenzhen) Company Limited）。

3.2 Ghidra 反编译结果

Ghidra headless 对 Weixin.exe 完成全量自动分析（58 秒），识别 7,080 个函数。入口点为标准 CRT 启动序列：

===== entry @ 1401cce00 =====
void entry(void)
{
  __security_init_cookie();   // 栈保护 cookie 初始化
  __scrt_common_main_seh();   // CRT 主启动例程
  return;
}

唯一导出函数 GetHandleVerifier 的反编译显示其采用自校验模式：先检查全局缓存，再通过 GetModuleHandleW(NULL) + GetProcAddress 解析自身导出，若解析结果与自身地址相同则调用验证回调——这是 Chromium 系（Base）handle verifier 的典型实现，用于调试期句柄泄漏检测。

依据
ghidra_java_funcs.txt（7,080 行函数地址/名称清单）、ghidra_java_decomp.txt（GetHandleVerifier 与 entry 的反编译输出）、ghidra_weixin_exe4.log（分析成功日志：Decompiler Switch Analysis 6.2s / x86 Constant Reference 11.1s / Stack 12.2s 等 24 个分析器全部通过）。

4.2 导出函数（117 个）——网络栈即 Cronet

117 个导出中约 100 个属于 mmcronet C++ 命名空间（GCC/MSVC 混合 mangling），覆盖：

  • mmcronet::Engine / EngineParams——Cronet 引擎生命周期，含 SetEnableHttp2 / SetEnableBrotli / SetEnableNetworkQualityEstimator / SetEnablePublicKeyPinningBypassForLocalTrustAnchors；
  • mmcronet::Fetch / Request / FetchWith——HTTP 请求原语；
  • TransferHandle / TransferOptions / TransferCallbacks——大文件传输抽象（取消/暂停/进度/指标）；
  • RequestBody::FromBytes / FromFile / FromString / Multipart——上传体构造。

业务导出仅 5 个：WeChatMain（主入口）、SetWeixinCallbackFunc、HostStartupExceptionReport、SetUseUserCA（自定义 CA 开关）、GetHandleVerifier。

依据
weixin_dll_exports.json：export count=117，dll_name=Weixin.dll，函数名清单含上述全部符号。Cronet 为 Chromium 网络栈的移动端/嵌入式封装库，CRONET-H1/H2/H3/UNK 协议标识字符串亦在二进制中发现（偏移 0x 段，见字符串证据）。

七、架构推断（基于以上证据）

Weixin.exe (启动器, 3 MB, CFG 开启)
    │  延迟加载 11 DLL → 定位并调用
    ▼
Weixin.dll (核心库, 195 MB, ~51 万函数)
    ├── WeChatMain() 主入口
    ├── mmcronet::*      ──→ Chromium Cronet 网络栈 (HTTP/2, QUIC, Brotli)
    ├── Mars (mars.cdn.proto.*, mars.smc) ──→ 长连接推送 + CDN 下载
    ├── Protobuf (micromsg/wmpf_host/finderlive) ──→ 业务协议序列化
    ├── SQLite + AES-128 ──→ 本地加密存储
    ├── Qt (.qtmetad) + Skia + ANGLE ──→ UI 渲染管线
    ├── mmmojo ──→ 跨进程组件框架
    └── 按需加载: VoipEngine / XPlayer / WeChatOcr / RadiumWMPF(小程序)

与旧版差异：4.x 新架构将原 WeChat.exe 单体拆分为启动器+核心库，主程序更名 Weixin.exe，网络栈从旧自研栈切换为 Chromium Cronet，UI 层引入 Qt 元对象系统（旧版为纯 Win32/DUI），小程序运行时 RadiumWMPF 独立为 412 MB 容器。

八、局限性说明

  • REA MCP 的 Ghidra provider 因 Windows 提升令牌对象所有权问题（Win32 5）在本机被拒，故采用 Ghidra headless 直接调用——分析引擎相同，仅交互层不同。
  • 195 MB 核心库未做全量 Ghidra 反编译（预计数小时），函数数 51 万为 .pdata 节区推算值（6 MB ÷ 12 B/RUNTIME_FUNCTION）。
  • 字符串证据为静态采样，未结合运行时行为验证；域名列表不代表完整网络端点集合。
  • 本报告仅基于本机安装的二进制文件（版本 4.1.15.55），不构成对腾讯任何协议的完整还原。
