## 二、根因分析

### Bug 1 根因：GitHub Actions 部署产物结构错乱

`deploy-promo.yml` 第 49-52 步直接在 `docs/promo/`（Pages 源目录）就地执行：
```
mkdir -p ./docs/promo/app
cp -r ./web-frontend/dist/* ./docs/promo/app/
```
并紧接着 `upload-pages-artifact` 上传 `./docs/promo`。

虽然此逻辑**在本地**看似正确，但从实际线上表现看（Web 应用出现在根、`/app/` 404），说明 Actions 中产物的最终结构被破坏了。可能的原因包括：
1. `actions/upload-pages-artifact` 在与 `configure-pages` 组合时，对嵌套 `app/` 子路径处理出现了合并问题；
2. 上一次构建产物的残留（来自 concurrency group 间的缓存或 Pages 内部 artifact 合并）污染了本次目录；
3. Vite `base: './'` 的产物被 Pages 当成 SPA 根页面，而未真正区分 promo 与 app 两套静态资源。

**核心修复思路**：不再复用 `docs/promo` 目录作为 Pages 上传源，而是新建一个**干净的 staging 目录**，按顺序拷贝两份完全独立的产物，保证上传前文件结构 100% 可控。

### Bug 2 根因：authStore mock 降级范围过窄

在 `authStore.ts` 中，`login()` 失败时的降级条件是：
```typescript
if (error instanceof ApiError && (error.status === 0 || error.status >= 500)) { ... mock fallback ... }
```
而 GitHub Pages 是纯静态托管，**所有 POST / PUT 请求都会被 CDN 拒绝**，返回 HTTP **405 Method Not Allowed**。由于 **405 既不是 0 也不是 ≥500**，降级条件未命中，错误直接透传给用户（"请求失败 (405)"）。

相同问题也存在于 `register()`、`loginWithThirdParty()`、`loginWithPhone()` 四个方法。

**核心修复思路**：将 404 / 405 等"后端不存在"类错误纳入降级范围，并对 `student1 / teacher1 / parent1` 等演示账号进一步做**短路处理**——无需等待网络请求失败就直接进入 mock 模式，彻底规避网络层不确定因素。

### Bug 3/4 根因：Login.tsx 第三方登录按钮文字构造 + 快速体验文案拼接

快速体验按钮的模板字符串在角色变量前后包含了空格，导致 `快速体验（ 学生 ）` 出现多余空格。QQ 登录按钮同时在 Lucide 图标下方 `<span>` 内渲染 "QQ" 图标替代文字 + "QQ登录" 描述文字，造成重复文本。

## 三、修复方案与步骤

### 阶段 A：修复部署产物结构（Bug 1）

**目标**：`/` 显示宣传页，`/app/` 加载 Web 应用（React SPA）。

**修改文件**：
- `.github/workflows/deploy-promo.yml`（重点重写合并步骤）

**具体修改**：

1. 将 "Merge web-frontend into promo/app" 重写为 "Assemble Pages artifact"：
   ```yaml
   - name: Assemble Pages artifact (promo@root + app@/app)
     run: |
       # 🟢 使用一个完全干净的 staging 目录，避免任何污染
       rm -rf ./pages-staging
       mkdir -p ./pages-staging

       # 1) 拷贝宣传页到 staging 根（promo 位于 /）
       cp -rT ./docs/promo ./pages-staging

       # 2) 拷贝 Web 应用到 staging/app（Web 位于 /app/）
       mkdir -p ./pages-staging/app
       cp -rT ./web-frontend/dist ./pages-staging/app

       # 3) 🔍 打印目录结构，让 Actions 日志可追溯
       echo "=== pages-staging/ 最终结构 (前 3 层) ==="
       find ./pages-staging -maxdepth 3 | sort
       echo "=== pages-staging/index.html 标题检查 ==="
       grep -oE '<title>[^<]*</title>' ./pages-staging/index.html || true
       echo "=== pages-staging/app/index.html 标题检查 ==="
       grep -oE '<title>[^<]*</title>' ./pages-staging/app/index.html || true
   ```
2. 将 `upload-pages-artifact` 的 `path` 从 `./docs/promo` 改为 `./pages-staging`。
3. 在 workflow 顶部的 `concurrency` 之后，增加一个 `env` 块：
   ```yaml
   env:
     PROMO_TITLE_MUST_CONTAIN: "你的情绪星球"   # 用于后续日志自检
   ```

> `cp -rT`（T = target-directory，no-implied-subdir）能避免 "如果目标已存在就把源塞进子目录" 这种 shell 复制行为的不确定性，比原先的 `cp -r dist/*` 更稳健。

### 阶段 B：修复登录 405 → mock 降级不生效（Bug 2）

**目标**：在无后端的静态托管场景下，"快速体验"（以及账号登录 `student1:123456`、第三方登录、手机号登录）1 秒内成功进入系统。

**修改文件**：
- `web-frontend/src/store/authStore.ts`

**具体修改**：

1. 抽出一个工具函数，判断是否应该走 mock 降级：
   ```typescript
   // 命中条件：① 断网 ② 后端不存在（404/405） ③ 服务端异常（≥500）
   function shouldUseMockFallback(err: unknown): boolean {
     if (!(err instanceof ApiError)) return false;
     return err.status === 0
       || err.status === 404
       || err.status === 405
       || err.status >= 500;
   }
   ```
2. 将 `login()`、`register()`、`loginWithThirdParty()`、`loginWithPhone()` 中的
   ```
   if (error instanceof ApiError && (error.status === 0 || error.status >= 500))
   ```
   全部替换为：
   ```
   if (shouldUseMockFallback(error))
   ```
3. **额外增加演示账号短路（推荐）**：在 `login()` 真正发起网络请求前加一段：
   ```typescript
   // 演示账号 → 直接走 mock，避免 405/网络抖动
   if ((credentials.username === 'student1' || credentials.username === 'teacher1' || credentials.username === 'parent1')
       && mockUsers[credentials.username]?.role === credentials.role) {
     const mockUser = mockUsers[credentials.username];
     set({ user: mockUser, token: 'mock-jwt-token', isLoggedIn: true,
           isLoading: false, loginMethod: 'credentials', isUsingMockData: true });
     return;
   }
   ```
   这段可确保「快速体验（学生）」按钮按下后**无任何 HTTP 请求**，瞬时进入主页。

### 阶段 C：修复 UI 文案与可访问性（Bug 3、Bug 4）

**修改文件**：
- `web-frontend/src/pages/Login.tsx`

**具体修改**：

1. **快速体验按钮（Bug 4）**：把 `快速体验（ ${roleConfig[role].label} ）` 中的空格改为 `快速体验（${roleConfig[role].label}）`（或中文风格 `快速体验·${roleConfig[role].label}模式`）。

3. 检查"微信 / Apple / 手机号"等同款按钮是否有同类问题，一并统一处理。

## 四、潜在风险与应对

| 风险 | 可能性 | 影响 | 应对 |
|------|--------|------|------|
| `configure-pages` 与 staging 目录结合，首次部署触发 Pages "未发布" 状态 | 低 | 短时间 404 | workflow 中加 `environment: github-pages` 不变；如卡住，手动在仓库 Settings → Pages 中触发一次 Re-run |
| authStore 改为直接 mock 演示账号后，真实后端若存在可能会被绕过 | 低 | 仅影响本地开发 / 生产后端部署后 | 用 `import.meta.env.PROD` 或 `VITE_API_BASE_URL` 做判断：有真实 API base 时不触发短路；无 API 时才跳过网络 |
| HashRouter 在 `/app/` 下，直接访问 `/app/#/student` 失败 | 极低 | 用户刷新子路由会出问题 | 当前 HashRouter 不依赖服务器 rewrite，只要 `/app/index.html` 正确加载即可，预计无问题；若将来切 BrowserRouter，再补 SPA 404 → index.html 回退规则 |
| 中文文案更新导致快照 / E2E 脚本误报 | 低 | 自动化测试失败 | 用"包含"逻辑代替全等匹配 |
